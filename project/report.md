# Отчет по проекту

## 1. Постановка задачи

Цель проекта - построить сервис, который по признакам бронирования отеля оценивает вероятность его отмены.

Практический смысл задачи:

- заранее выявлять рискованные бронирования;
- корректировать операционное планирование;
- использовать риск-оценку в бизнес-процессах подтверждения брони.

Целевая переменная:

- `is_canceled` - бинарный признак отмены бронирования.

Основные метрики:

- `ROC-AUC` как основная ранжирующая метрика;
- `F1` для баланса precision/recall;
- `PR-AUC` как дополнительная метрика для задачи бинарной классификации.

---

## 2. Данные

Базовая предметная область проекта опирается на датасет **Hotel Booking Demand**.

В рабочей версии проекта используется файл `data/hotel_bookings.csv`.
Используемые признаки:

- числовые: `lead_time`, `adr`, `adults`, `children`, `babies`, `previous_cancellations`, `previous_bookings_not_canceled`, `booking_changes`, `days_in_waiting_list`, `required_car_parking_spaces`, `total_of_special_requests`, `stays_in_weekend_nights`, `stays_in_week_nights`;
- категориальные: `hotel`, `meal`, `market_segment`, `distribution_channel`, `deposit_type`, `customer_type`, `reserved_room_type`.

---

## 3. EDA и основные выводы

Разведочный анализ выполнен в `notebooks/01_eda.ipynb`. В ноутбуке были проверены:

- баланс целевой переменной `is_canceled`;
- распределения ключевых числовых признаков;
- различия между классами по `lead_time`, `adr`, `previous_cancellations`, `total_of_special_requests`;
- связь категории бронирования с риском отмены;
- сезонные различия по месяцам заезда.

Ключевые результаты EDA:

- доля отмененных бронирований составляет `37.04%`, то есть задача умеренно несбалансирована, но не экстремально;
- средний `lead_time` для отмененных бронирований равен `144.85`, а для неотмененных `79.98`, поэтому длинный горизонт между бронированием и заездом действительно связан с более высоким риском отмены;
- среднее число специальных запросов у отмененных бронирований равно `0.33`, а у неотмененных `0.71`, что подтверждает гипотезу о том, что более “вовлеченные” клиенты чаще доводят бронирование до заезда;
- по таблицам сопряженности и графикам видно, что `deposit_type`, `market_segment`, `customer_type` и `hotel` заметно разделяют классы и должны давать полезный вклад модели;
- признаки прошлой истории клиента, включая `previous_cancellations`, также оказываются информативными: у клиентов с опытом отмен риск новой отмены выше;
- в данных наблюдаются выбросы и асимметричные распределения по ряду числовых признаков, поэтому использование устойчивого препроцессинга с импутацией и масштабированием оправдано.

Вывод по EDA: для задачи достаточно как табличных числовых, так и категориальных признаков, а наиболее сильными кандидатами на предикторы выступают `lead_time`, `deposit_type`, `market_segment`, `previous_cancellations` и `total_of_special_requests`.

## 4. Модели

В проекте сравниваются три подхода:

1. `LogisticRegression` - интерпретируемый baseline.
2. `RandomForestClassifier` - нелинейная классическая модель.
3. `MLPClassifier` - простой нейросетевой baseline.

Выбор такого набора моделей удобен для защиты:

- есть простая линейная база;
- есть более сильная классическая нелинейная модель;
- есть нейросетевой baseline, что хорошо связано с тематикой курса.

---

## 5. Экспериментальный дизайн

- train/test split с `stratify=y`;
- единый препроцессинг:
  - медианная импутация для числовых признаков;
  - most-frequent импутация для категориальных;
  - `StandardScaler` для числовых;
  - `OneHotEncoder` для категориальных;
- сравнение моделей на одном и том же разбиении;
- сохранение метрик в `artifacts/metrics.json`.

---

## 6. Выбор финальной модели

Финальная модель выбирается по следующим принципам:

- лучший `ROC-AUC`;
- отсутствие сильного провала по `F1`;
- устойчивость поведения на тестовом наборе;
- простота сопровождения и интеграции в сервис.

Результаты текущего запуска на полном датасете:

| Модель | ROC-AUC | F1 | PR-AUC |
|---|---:|---:|---:|
| Logistic Regression | 0.8502 | 0.6994 | 0.8239 |
| Random Forest | 0.8766 | 0.6861 | 0.8484 |
| MLPClassifier | 0.8917 | 0.7349 | 0.8637 |

Финальный выбор: **MLPClassifier**.

Причины выбора:

- лучший `ROC-AUC` среди всех сравниваемых моделей;
- лучшая `PR-AUC`, что важно для качества вероятностного ранжирования;
- лучшая `F1`, то есть более удачный баланс между precision и recall;
- модель остается достаточно легкой для локального запуска и интеграции в FastAPI-сервис.

---

## 7. Сервис

REST API реализован на FastAPI.

Основные endpoint'ы:

- `GET /health` - служебная проверка доступности сервиса и артефактов;
- `POST /predict` - получение вероятности отмены и класса риска.

Формат ответа:

- `cancel_probability` - вероятность отмены;
- `risk_level` - `low`, `medium` или `high`;
- `model_name` - имя текущей модели.
